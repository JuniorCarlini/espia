# 0012. Use Tucano for the settings dialog, select, and buttons

- **Status:** Accepted
- **Date:** 2026-09-24

## Context

The settings UI (a modal, a language `<select>`, several buttons) was
hand-built: a div-based overlay for the "modal", a bare native `<select>`,
and Tailwind-styled buttons. It worked, but two things fell short of what a
small component library gets for free:

- The native `<select>` opens as an OS-level popup, outside the app's own
  window and theme — jarring next to everything else, and (found while
  testing it) awkward to drive with anything but real user input, since it
  isn't part of the page at all.
- The hand-rolled modal had none of what a `<dialog>`-based one gets by
  default: focus trapping, Escape-to-close, and correct layering, all
  reimplemented by hand or simply missing.

[Tucano](https://juniorcarlini.github.io/tucano/) — a small, dependency-free
JS + CSS component library — covers exactly this (Modal, Select, Button,
and more) as plain HTML enhanced via `data-tuc-*` attributes or thin JS
classes, over native elements (`<dialog>`, `<select>`) rather than replacing
them. No JS framework, matching [ADR 0004](0004-desktop-agent-stack.md)'s
"no framework" call for the frontend.

## Decision

- **Vendor the built files locally**, not a CDN: `npm install tucano`, then
  `npm run vendor` copies `tucano.min.css` and `tucano.esm.js` into
  `agent/src/vendor/tucano/` (gitignored, regenerated by that script — same
  treatment as `styles.css`). `beforeDevCommand`/`beforeBuildCommand` run it
  automatically (`npm run prep` = `vendor` + `build:css`). A CDN dependency
  would contradict the agent's own design: everything except the weather
  card is explicitly local-only, and the app's own chrome shouldn't need a
  network connection to render.
- **Retheme via its CSS custom properties**, not by overriding its classes:
  Tucano's components read colors, radii, and the rest from `--tuc-*`
  variables. `input.css` remaps those onto the tokens already defined in its
  own `@theme` block (`--tuc-accent: var(--color-brand)`, and so on) in one
  place, after `tucano.min.css` loads so the remap wins by source order —
  see the `:root` block at the end of `input.css`.
- **Mix Tucano's atomic classes with Tailwind utilities directly** in
  markup (`class="tuc-btn is-primary is-block"` next to plain utility
  classes elsewhere) — its docs describe exactly this as supported, and nothing
  here needed more structure than that.
- **The Modal is fully declarative**: a `<dialog class="tuc-modal">` plus a
  trigger button carrying `data-tuc-modal="#id"`, wired up by Tucano's own
  `init()` (called once on load) — no JS reference to a `Modal` instance
  needed anywhere in `main.js`.
- **The Select is constructed explicitly** (`new Select('#settings-language',
  {onChange, ...})`) rather than left to auto-init, since the app needs a
  reference for `setValue()` (reflecting a loaded setting into the field)
  and an `onChange` hook (saving a change back to the agent) — auto-init
  alone gives neither.

## Consequences

- The settings dialog now gets focus management and Escape/backdrop-close
  for free, and the language picker renders as an in-page, themed dropdown
  instead of a native OS popup — both fixed by adopting the component,
  not by extending the hand-rolled versions further.
- One more moving part to keep in sync: `npm run vendor` must be re-run
  (automatic via `prep`, but worth knowing) after bumping the `tucano`
  version in `package.json`.
- Retheming through custom properties means future Tucano components (a
  toast for a future "settings saved" confirmation, say) inherit the same
  dark/brand look with no per-component styling work — the tokens are
  already mapped once.

## Alternatives considered

- **Load Tucano from its jsDelivr CDN** (as its own docs show) — simpler to
  wire up, but makes the app's core UI depend on a network connection to
  even render its chrome, which nothing else in this codebase does.
- **Keep extending the hand-rolled modal/select** (manual focus trap, an
  in-house dropdown) — deliverable, but re-implements exactly what a
  purpose-built, already-available component does correctly.
